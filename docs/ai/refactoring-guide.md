# ソフトウェアリファクタリング戦略ガイド

リファクタリングとは、ソフトウェアの外部的な振る舞い（機能）を変えることなく、内部構造を改善し、理解しやすく修正しやすい状態にするプロセスです。本ガイドは、日々のコーディングから大規模なレガシーシステムの近代化まで、開発者が迷わずにコードを改善するための指針を提供します。

## 1. マインドセットと原則

リファクタリングを成功させるための心構えです。

- **「二つの帽子」の原則**:
  - 開発中は「機能追加」と「リファクタリング」の帽子を明確に使い分けます。
  - 機能追加中は構造を気にせずテストを通すことに集中し、リファクタリング中は機能を一切変更せずに構造の改善のみに集中します。
- **ボーイスカウトの規則**:
  - 「来た時よりも美しくして立ち去る」という原則です。大規模な修正を待つのではなく、ファイルを開くたびに変数名の変更や不要なコメントの削除など、小さな改善を積み重ねます。
- **経済的合理性**:
  - リファクタリングは美学のためではなく、開発速度（ベロシティ）を維持・向上させるための経済的な投資です。内部品質が高いコードは、機能追加のコストを低く抑えられます。

## 2. 準備フェーズ：安全網の構築

テストのないコードをリファクタリングするのはギャンブルです。まずは安全網を構築します。

- **レガシーコードのジレンマへの対処**:
  - 「テストがないコード＝レガシーコード」と定義されます。テストを書くためにコードを変更しなければならないジレンマに対し、**接合部（Seam）**を見つけて依存関係を切り離し、テストを導入します。
- **仕様化テスト（Characterization Test）**:
  - コードが「どうあるべきか」ではなく「現在どう動いているか」を記録するテスト（ゴールデンマスターとも呼ばれる）を作成し、リファクタリングによる挙動の変化を検知できるようにします。
- **優先順位の決定**:
  - すべてを修正する必要はありません。「変更頻度（Churn）」が高く、「複雑度（Complexity）」が高い領域（ホットスポット）を最優先で改善します。

## 3. 実践テクニック：コードの不吉な匂い（Code Smells）への対処

コードが発する「不吉な匂い」を検知し、適切な「脱臭（リファクタリング）」技法を適用します。

### A. 肥大化（Bloaters）への対処

コード、メソッド、クラスが巨大化し、管理不能になった状態です。

| 不吉な匂い               | 兆候                                               | リファクタリング技法                                                                                           |
| :----------------------- | :------------------------------------------------- | :------------------------------------------------------------------------------------------------------------- |
| **長いメソッド**         | 1つのメソッドが複数の責任を持っている              | **メソッドの抽出 (Extract Method)**: 意味のある単位でコードを切り出し、意図を表す名前をつける。                |
| **巨大なクラス**         | クラスが多くのフィールドやメソッドを持ちすぎている | **クラスの抽出 (Extract Class)**: 関連するフィールドとメソッドを新しいクラスに移動する。                       |
| **基本データ型への執着** | 電話番号や金額をStringやIntで扱っている            | **オブジェクトによる基本データ型の置換**: `TelephoneNumber`や`Money`クラスを作成し、ロジックをカプセル化する。 |
| **長い引数リスト**       | 引数が多すぎて理解しにくい                         | **引数オブジェクトの導入**: 引数をまとめたクラスを作成して渡す。                                               |

### B. 複雑な条件分岐の簡素化

ネストが深く、理解しにくい条件分岐を整理します。

- **ガード節による入れ子条件の記述の置き換え**:
  - 正常系の処理を明確にするため、特殊な条件（エラーケースなど）はメソッドの冒頭で早期リターンさせ、ネストを浅くします。
- **条件記述の統合**:
  - 同じ結果を返す複数の条件判定がある場合、それらを論理演算子で結合して一つの条件式にします。
- **条件記述のポリモーフィズムによる置き換え**:
  - `switch`文や`if-else`で型に応じた処理を分岐させている場合、サブクラスを作成してオーバーライドを利用し、分岐を削除します。

### C. データの組織化と移動

適切な場所にデータと振る舞いを配置します。

- **機能の羨望 (Feature Envy)**:
  - あるメソッドが、自クラスよりも他クラスのデータを頻繁に使用している場合、そのメソッドをデータがあるクラスへ移動させます（**メソッドの移動**）。
- **データクラス**:
  - ゲッターとセッターしか持たないクラスは、他のクラスから振る舞いを移動させ、責任を持たせます。

## 4. 大規模リファクタリング戦略

システム全体に関わる変更や、レガシーシステムの刷新における戦略です。

- **ストラングラー・フィグ・パターン（絞め殺しの木）**:
  - 既存のレガシーシステム（宿主）を生かしたまま、新しいシステム（イチジクの木）をその周囲に構築し、徐々に機能を移行させる手法です。
  - プロキシ（APIゲートウェイなど）を配置し、特定のリクエストを新システムへルーティングすることで、段階的な移行とリスク分散を実現します。
- **ミカドメソッド (Mikado Method)**:
  - 大規模な変更を行う際、ゴールから逆算して依存関係をグラフ化（ミカドグラフ）し、小さなステップで前提条件を解消していく手法です。
  - 変更がシステムを壊した場合は直ちに**Undo（元に戻す）**し、前提条件を解決してから再試行することで、常にコードベースを壊さない状態に保ちます。
- **抽象化による分岐 (Branch by Abstraction)**:
  - 長期間のブランチを作成する代わりに、コード内に抽象化レイヤーを設け、新旧の実装を切り替えられるようにします。これにより、未完成のコードを含みつつ継続的な統合が可能になります。

## 5. 絶対に避けるべきこと

- **ビッグバン・リライト（完全な書き直し）**:
  - 既存コードを捨ててゼロから書き直すことは、多くの場合「戦略的な誤り」です（Netscapeの失敗事例が有名）。
  - 既存コードにはドキュメント化されていない数多くのバグ修正やエッジケースへの対応（ドメイン知識）が含まれており、それらを失うリスクと、再開発中に市場の変化に追随できなくなるリスクがあります。

## 6. AIツールの活用と注意点

- **AIによる支援**: GitHub CopilotやQodoなどのAIツールは、テストの生成、コードの複雑性の検出、リファクタリングの提案に役立ちます。特に、コンテキスト（文脈）を理解した提案は、見落としがちな依存関係の特定に有用です。
- **注意点**: AIはリファクタリングの指示に対して、機能（振る舞い）を変えてしまったり、過度な簡略化を行ったりするリスクがあります。「コードの挙動を変えない」というリファクタリングの原則を人間がレビューし、テストで保証する必要があります。
